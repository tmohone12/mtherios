`npm run app:dev` brings up PostgreSQL and Qdrant, runs migrations, and starts development mode. `npm run app:start` serves an existing production build; it does not build or run the dependency/migration scripts. `npm run app:build` builds and then starts production. `npm run dev` starts Vite alone.

Local AI is opt-in. [Start.bat](Start.bat) and [start.ps1](start.ps1) offer separate choices for Kev-9B decisions and Ollama/local embeddings, each defaulting to off. The selections are saved by [select-local-ai.mjs](scripts/select-local-ai.mjs) without changing provider profiles or embedding models. Noninteractive startup uses `localKevEnabled` and `localEmbeddingsEnabled` from runtime configuration, both false by default; CLI overrides are `--local-kev` / `--no-local-kev` and `--local-embeddings` / `--no-local-embeddings`, with environment equivalents `MYTHENGINE_LOCAL_KEV` and `MYTHENGINE_LOCAL_EMBEDDINGS`. Off mode blocks local Kev/Ollama requests and disables configured Ollama embeddings; wiki search retains its exact-search fallback and existing vectors are retained. Remote embedding providers remain available.

When opted in, [mtheriosd.mjs](scripts/mtheriosd.mjs) starts Ollama if configured embeddings need it and Ollama is down. Kev starts only when enabled and `data/models/kev/.venv-rocm/Scripts/python.exe` exists, using loopback port 8008. The upstream Kev checkout and Python environment live in ignored `data/models/kev`; startup does not install dependencies or wait for the checkpoint to load. Sidecar logs live under `data/logs/`. `OLLAMA_EMBED_NUM_GPU=0` (or `ollamaEmbedNumGpu: 0` in local config) keeps Ollama embeddings on CPU.

Configuration is owned by [runtime-config.mjs](scripts/runtime-config.mjs), shared by the daemon, CLI/MCP, Vite, database/migrations, server settings and wiki adapters. Precedence: CLI > new environment aliases > legacy/generic environment > selected config > defaults. `mythengine.config.json` wins over `mtherios.config.json`; secret-bearing files are not merged. [The example](mythengine.config.example.json) documents the new defaults.

The isolated Compose project is `mythengine`, with loopback app 5174, PostgreSQL 5433 and Qdrant 6335/6336. Data defaults to `./data`; external paths and known original service targets fail unless intentional sharing is explicitly enabled. Jobs and wiki auto-index default off. [backend.mjs](scripts/backend.mjs) fixes Compose project/file ownership for up/down/config; down retains volumes. `npm run app:config` reports sanitized targets, and `npm run app:status` verifies the running process. A data-directory copy alone is not a PostgreSQL backup.

[build.mjs](scripts/build.mjs) records source and artifact SHA-256 fingerprints in `build/mythengine-build.json`; production startup verifies artifact integrity and exposes the fingerprints through status. Runtime identity does not assert the current source still matches the build. Legacy MCP names remain aliases without a removal date; database/storage/wire identifiers are retained for compatibility. The new origin isolates browser state; new PWA caches use owned MythEngine prefixes. [Phase 0 evidence](docs/mythengine-phase0-2026-09-21.md) describes the qualified scope.

## Storage and authority

```text
Player action / import / authorized edit
  -> persisted source evidence
  -> structured proposals and validation
  -> PostgreSQL campaign records and provenance
  -> outbox jobs and versioned projections
  -> memory retrieval / Markdown vault / optional indexes
  -> browser projection
```

[The database schema](src/lib/server/db/schema.ts) owns stories, entries, entities and aliases, relationships, factions and projects, facts, NPC beliefs, agreements, events, threads, state patches, proposals, source references, continuity warnings, memory nodes, chapters, arcs, sagas, and backend jobs.

Transcript entries are durable evidence; prose does not automatically establish every inferred fact as accepted state. Canonical writes preserve IDs, provenance, and relevant revision checks. NPC beliefs and planned/scheduled events are separate from current truth.

Generated Markdown is a readable projection. Qdrant indexes vault content; pgvector supports backend memory embeddings. Neither vector representation is authority. IndexedDB/Dexie serves the client cache and remaining local/legacy compatibility paths for backend-bound stories.

## Server turn and prompt flow

Primary implementation: [turn/orchestrator.ts](src/lib/server/turn/orchestrator.ts). The separate [engine/orchestrator.ts](src/lib/server/engine/orchestrator.ts) serves engine orchestration; do not confuse the two. [agentRuns.ts](src/lib/server/engine/agentRuns.ts) owns durable GM model-tool runs, question continuation and tool receipts; every new run uses the Pi runtime (the legacy planner runtime is retired for new turns — a saved `gmPiRuntime: false` is ignored — while existing legacy run records stay readable); [generatedNames.ts](src/lib/server/engine/generatedNames.ts) validates bounded GM name candidates without creating canon. [agentRunGuard.ts](src/lib/server/engine/agentRunGuard.ts) prevents a second advancing turn while one is pending. Migrations 0030–0032 own the run ledger and persisted provider decisions, and [run-stream](src/routes/api/engine/run-stream/+server.ts) projects its cursor-ordered events. The run reaches the existing turn owner only when ready to narrate. The browser composer ([ActionInput.svelte](src/lib/components/story/ActionInput.svelte)) submits every narrative turn through `agent.run.start`, then follows the run with the event stream and a 2-second poll, answers questions and rolls with `agent.run.respond`, stops it with `agent.run.cancel`, and recovers it after a reload or a lost response by client turn ID; [actionInput.ts](src/lib/components/story/actionInput.ts) owns the start/recovery and draft-restore decisions. `/api/turn` and `/api/turn/stream` remain server routes for the CLI and evaluation scripts; the browser no longer calls them.

Model configuration has one owner, [modelSettings.ts](src/lib/server/engine/modelSettings.ts), over the shared registry in [modelTasks.ts](src/lib/contracts/modelTasks.ts). A **model profile** (`model_profiles`) is a provider connection, model, capabilities, context limit and generation defaults. Each **role** (`model_roles`: GameMaster, Classifier, Summaries, optional Decisions, plus optional Authoring and Image) selects a profile and explicit fallback profiles. Each **task** is a registered operation keyed by its legacy service ID (`narrative` is the GameMaster's narration task, `classifier` turn extraction, `memory`/`arcCondensation` summaries, `actorDecision` Decisions, and so on) with an owner, trigger, contract, default enablement and request budget. `model_task_overrides` stores only explicit differences; no row means full inheritance. Resolution is read-only: override profile, else role profile, else (GameMaster/Classifier/Summaries only) the environment default; Decisions, Authoring and Image never inherit, and Decisions requires a supported decision model. The browser-only `sagaCondensation`, `loreManagement` and `entryRefinement` tasks are retired alongside `worldSimulation` and `styleReviewer`; saved overrides stay readable. Nothing falls back across roles implicitly: summaries use only the Summaries task and its explicit fallback profiles, extraction never borrows the GameMaster, and Lore Master research never borrows the Classifier. Unconfigured tasks fail with a `Model configuration needed:` reason, classified as a `configuration` failure that may be retried manually after settings change. Migration 0054 converted the legacy `llm_service_settings` rows (retained unchanged for rollback) by diffing each task against its role. `settings.models.get`/`settings.models.save` (revision-checked) back [ModelRolesPanel.svelte](src/lib/components/settings/ModelRolesPanel.svelte); the legacy `settings.llm.*` commands and [llmSettings.ts](src/lib/server/engine/llmSettings.ts) remain a compatibility facade that stores values equal to the inherited ones as inheritance. GM turn receipts list each used task's effective profile, revision, source and limits (`modelTasks`).

The optional `dialogue` service runs after the GameMaster draft and any roll continuation. [dialoguePass.ts](src/lib/server/turn/dialoguePass.ts) attributes known NPC speech and gives each speaker a separate bounded request with that speaker's actor card, selected learned beliefs, applicable actor decision, nearby draft prose, recent exchanges, and player action. GM tool observations and other speakers' private cards are excluded. It may replace only quoted NPC speech; invalid or failed output leaves the whole GM draft intact. The service is off until configured in AI Services. Dialogue coverage defaults to all eligible speech; the optional important-exchanges mode skips clear routine greetings. The final result is streamed and persisted once.

World time is owned by [worldClock.ts](src/lib/server/events/worldClock.ts) (`world_clocks`, `world_time_changes`, migration 0057): numeric minutes since an anchor day, a calendar (hours per day; optional months, weekdays and era for rollover), a precision (`minute`, `approximate`, `day`, `unknown`), a branch and a revision, separate from the turn counter and worker timestamps. The narration header and the classifier's `time_delta` are proposals: an exact stated duration outranks the header, the header outranks an estimate; the clock rejects rewinds and oversized jumps, applies each turn once under `turn:<assistant entry>` (so delayed extraction and repeats cannot re-advance), and records before/after values. OOC, non-canon, thought and parallel-POV turns propose nothing, and summaries, rebuilds and imports never call it. A wait stops at the first event scheduled by world time (`timeline.schedule` `delayWorldMinutes`, stored as `metadata.dueWorldMinutes` with no `scheduledTurn`); reached events become `due`, never resolved. `stories.current_world_time` is the derived label (a consistent header keeps the narrator's wording); a label changed outside the clock (import, checkpoint revert, operator edit) re-anchors it on the next change, recorded as `external_label`. `world.clock.status` and `world.clock.configure` (calendar or explicit time, named reviewer) are the operator surface. Faction world-time wakes still fire when the label changes; world-day gates still read only exact `Day N` labels. [dueEventFeedback.ts](src/lib/server/events/dueEventFeedback.ts) checks final-narration evidence, snapshotted due-event revisions and the persisted source before a due event can be marked realized through synchronous or deferred extraction; ambiguous outcomes stay unresolved. The same extraction pass checks whether an optional faction cue surfaced in final prose; its presentation receipt never realizes the underlying world event. Story presentation metadata holds the latest attempt status so pending cues do not recur after a scene change, and only feedback for that latest entry can release an unwritten cue.

Prepared contexts are cached by story/client turn identity and request fingerprint. Reuse checks story server version, narrative settings, authored context, scene checkpoint, and the applied Plot Director/presentation state, including current turn and location. A checkpoint refresh or Director retirement can change guidance without changing story version.

The compact campaign continuity brief lives in PostgreSQL `stories.metadata.campaignState`, using [campaignState.ts](src/lib/contracts/campaignState.ts). Sync and deferred state extraction propose up to eight source-quoted topic changes; the locked canonical writer validates primary-POV narration, source position and expected prior source ID before replacing a topic. At 32 topics new keys are rejected with warnings rather than silently evicting milestones; related changes should reuse existing keys. The brief is supplied before historical context, has retained-record receipt tracking, and a normal turn fails explicitly if its required bullets cannot fit the context budget. It is GM reference, not universal NPC knowledge. The World state drawer projects these bullets and their supporting quotes. Historical retrieval selects by relevance, then displays dated selected records chronologically; undated records retain relevance order. This does not replay or automatically backfill old campaigns; `scripts/seed-veil-campaign-state.mjs` provides a dry-run-first, five-anchor Veil backfill.

### Prompt settings and evidence

Narrator instructions come from the story's **narrative preset** revision: [narrativePreset.ts](src/lib/server/turn/narrativePreset.ts) composes editable style sections and locked engine blocks (authority, workflow, turn boundary, NPC agency/knowledge, header and dice contracts) with a six-variable vocabulary, and [promptPresets.ts](src/lib/server/engine/promptPresets.ts) owns immutable revisions (migration 0055), explicit per-story selection (`story_prompt_presets`) and the default preset's designated revision for stories without one. Saving a revision never changes a pinned story; applying it is explicit. GM receipts record the preset, revision and content hash. Story genre packs live in [storyPromptPacks.ts](src/lib/components/wizard/storyPromptPacks.ts) and enter presets through variables. Settings → Prompts uses `prompts.presets.*`; `GET /api/settings/prompts/narrative` previews a story's effective preset. The resolved `narrative` task supplies provider/model/reasoning, context/output controls, and the legacy narrative `systemPromptOverride` task field, which applies only before preset storage exists (migration 0055 turned a saved override into the default preset). Inspect the story's preset revision before diagnosing style.

`turn.preview` and `/api/debug/prompt-packet/<storyId>` inspect server preparation. Preview occurs before tool observations and provider execution. [promptReceipt.ts](src/lib/server/turn/promptReceipt.ts) tracks retained source spans, complete/partial/omitted records, payload sections, and primary/roll-continuation request summaries. These token estimates exclude provider wire framing; they are not a billing receipt. The narrator caches campaign history as a stable system prefix. Anthropic-compatible requests put ordinary location-only wiki context in a second marked system cache segment so a changed wiki lookup can still reuse the history prefix; action-specific wiki results remain dynamic. NanoGPT puts changing wiki context after dialogue with the rest of the current turn context.

The browser exposes this through [ContextWindow.svelte](src/lib/components/story/ContextWindow.svelte), [ContextSelection.svelte](src/lib/components/story/ContextSelection.svelte), and [PromptsPanel.svelte](src/lib/components/settings/PromptsPanel.svelte). The context window shows only the last recorded receipt, labelled as recorded, beside the next-turn budget setting (0 = Auto, sized by the server from the GameMaster model); the composer's "Preview context" runs `turn.preview`. Neither computes a browser-side prompt estimate. Actual provider request diagnostics also live in [apiCallLogs.ts](src/lib/server/engine/apiCallLogs.ts).

[terminalSettings.ts](src/lib/services/terminalSettings.ts) mirrors the server's effective task settings into browser state on app startup, settings open, and explicit refresh; an inherited task stays inherited in the browser and its saves send parameters only, never a resolved model as an override. Mirrored profiles carry key references, not secret values. Narrative generation and context controls patch only their edited fields; memory-budget changes do not rewrite LLM settings. Service saves target changed services and never resend cached secrets by default. Provider credential replacement is an explicit save. Already-open clients need a reload to adopt this behavior; it is not a server-side rejection of legacy clients.

Keep direct GM/OOC control input separate from narrative evidence, and preserve parallel-POV and NPC knowledge boundaries. Parallel-POV preparation excludes unrelated secret retrieval and timeline records before the prompt is compiled; its deterministic memory read keeps that same visibility scope. Plot guidance does not override established scene evidence or the player's action.

## Memory, retrieval, and durable processing

Narration and roll continuations omit `max_tokens` on OpenAI-compatible transports (including OpenRouter), irrespective of the saved service cap. Full returned text and provider-reported completion/total/reasoning usage are retained; completion usage already includes reasoning and must not be double-counted. Native Anthropic still requires an explicit `max_tokens` value. Input/context safety reserves and bounded specialist outputs are separate from narrative output caps. Provider-imposed output limits remain observable through finish reasons.

[retrieval.ts](src/lib/server/memory/retrieval.ts) combines canonical records, event/memory projections, agreements and beliefs, transcript recall, and optional embedding-backed sources. [ranking.ts](src/lib/server/memory/ranking.ts) ranks candidates; visibility, temporal state, and control/POV filtering matter before caps. [retrievalSource.ts](src/lib/server/memory/retrievalSource.ts) bounds optional reads and reports degraded sources while retaining successful ones.

Lexical candidates use weighted full-text relevance before the 80-row cap and match individual meaningful query terms. Retrieval then resolves explicit supersession/source links and revision-topic dependencies independently of query wording (at most four passes, 1,000 related rows per pass; overflow fails rather than silently returning stale candidates). Corrections inherit linked relevance within the same campaign and belief owner; temporal/visibility exclusions still decide what can be rendered. This does not infer semantic corrections in unrelated summaries or repair missing extraction jobs. The memory benchmark includes candidate-cap and low-importance correction-chain regressions.

[canonical.ts](src/lib/server/memory/canonical.ts) maintains canonical retrieval projections. [sceneCheckpoint.ts](src/lib/server/memory/sceneCheckpoint.ts) derives bounded, source-linked scene state with branch/scene boundaries and excludes interlude/control material from primary-scene knowledge.

[The outbox](src/lib/server/jobs/outbox.ts) and [processor](src/lib/server/jobs/processor.ts) own retryable durable work, including:

- State extraction and continuity audit.
- Scene checkpoint refresh and event/canonical retrieval projections.
- Chapter summarization, arc rollup, and automatic saga rollup.
- Faction pressure, world simulation ticks, and Plot Director planning.
- Story-vault sync and optional memory embeddings.

The existing `extract_turn_state` job is the Memory & Context Turn Memory task: its job metadata records both transcript source IDs, and its source/version checks and retry semantics remain the sole durable extraction path. Sync and deferred extraction each allow one compact repair after invalid output, including an empty response that exhausted its output limit; that case lowers reasoning effort and raises the repair cap within the existing limit. A repair still validates the entire patch before canonical writes. The reader can inspect extraction coverage in [MemoryProcessingStatus.svelte](src/lib/components/story/MemoryProcessingStatus.svelte). Player Guidance uses the bounded [SuggestionsService.ts](src/lib/services/ai/generation/SuggestionsService.ts) only on recent player-visible transcript entries; its output is optional and never submits a turn. The unused Action Choices and Style Review services and the separate Wiki Lint workflow are retired. Wiki search/context and canonical write validation remain active.

[chapterCadence.ts](src/lib/services/chapterCadence.ts) owns the fixed cadence: 20 completed player/narrator turns per chapter, then 10 consecutive chapters per arc, with no trailing buffer. Legacy settings keys remain compatible but cannot override this rule. Accepted narration after a GM correction remains supplementary evidence without counting the GM instruction as a player turn. [summaryGeneration.ts](src/lib/server/jobs/summaryGeneration.ts) sends full source windows and validates one chronological account for every source; missing model output fails the job. The reader-facing summary is a connected chronological narrative, while the ordered source accounts remain complete audit evidence. Oversized chapters and arcs split into source-complete subwindows; synthesis consumes their retained accounts. Arc generation prefers validated chapter accounts over prose and excludes event-derived change lists from its factual input. Historical facts come from transcript narration, not extracted event descriptions. Arc persistence refreshes coverage and numbering under the story lock so competing jobs cannot duplicate chapter coverage or arc numbers, and queues its saga rollup and Director review in the same transaction. The World drawer's "Write arc now" control appears only when `selectArcRollupBatches` finds the next 10 consecutive uncovered chapters, runs `jobs.rollupArc` (a `jobs.rollupArc` `chaptersPerArc` argument is accepted and ignored), shows the job's failure or "not written" reason, and then refreshes the campaign projection. Completed or failed `rollup_arc` and `rollup_saga` jobs also trigger a projection refresh through the engine stream. Sagas are rolled up only by the job the arc transaction queues; there is no manual saga control. The `chapter.*`/`arc.*` record commands remain for author edits: `chapter.upsert` keeps the stored account when the incoming summary is its unchanged condensed display form, and `arc.create`/`arc.upsert` accept a new or changed chapter set only when every chapter is saved in the story, listed once, and not in another arc.

The chapter commit in [chapterCheckpoint.ts](src/lib/server/jobs/chapterCheckpoint.ts) (`createChapterCheckpoint`, dispatched by [processor.ts](src/lib/server/jobs/processor.ts) together with the `chapter_threads`/`chapter_characters` consumers) allocates the story revision and writes the chapter, its memory projection, any accepted campaign-fact review, a `metadata.completion` receipt, and every consumer job in one source-locked transaction; the chapter is complete when that transaction commits. [outbox.ts](src/lib/server/jobs/outbox.ts) (`enqueueChapterFollowUpJobs`) keys each consumer to the chapter ID and revision: `rollup_arc`, `chapter_threads` (applies the thread plan saved in its payload and queues Director review), `chapter_characters` (character reference/context proposals and the continuity refresh), `update_faction_pressure` (only when the chapter has source events), `embed_memory_nodes`, and `sync_story_vault`. A consumer skips a missing or rebuilt chapter revision; thread updates apply only to threads still at their snapshot revision, and the thread receipt commits with its writes. A consumer failure leaves the chapter complete and is retried on its own row (`jobs.retry` accepts these types) without regenerating the chapter or repeating another consumer's effects. The chapter row never changes after commit, because arc revalidation compares it.

[chapterWindows.ts](src/lib/server/jobs/chapterWindows.ts) owns the chapter window lifecycle shared by the live worker, the reviewed chapter-only runner, and historical rebuilds. `chapter_windows` is the logical slot (story, primary scope, number); each `chapter_window_attempts` revision freezes the exact source entry IDs and a transcript fingerprint over those rows and every other row in the window's range (content, pairing, branch, and eligibility metadata; turn receipts excluded), plus scope/POV, the projection compiler and the summarizer revision. States: `waiting` (classifier work on the window's turns still queued or running; bounded, then recorded as a gap), `ready`, `generating` (one leased generator; duplicates return `window_generating` without a request), `validated` (draft saved), `committed` (in the chapter transaction), `retryable_failure`, `needs_configuration`, `uncertain_dispatch` (held until `chapters.windows.reconcile`), and `invalidated`. New turns never change a frozen window; a source edit or boundary change invalidates the revision with the changed IDs and a new revision is frozen. Generation inputs (sources, event/thread evidence, campaign facts) are frozen on first claim, so a restart repeats the same request and the summary checkpoints reuse its result; a validated draft is committed without another request. Extracted events are attached at commit, so a late extraction joins the chapter instead of discarding its summary; failed or outdated extraction is recorded in `completion.extraction`. `chapters.windows.status` reports the current window, recent revisions, and contiguous summarized coverage with history gaps. A memory window is archival: it is not a narrative chapter ending, and the narrator keeps the last two exchanges across the boundary.

The chapter-only runner ([chapterSummaryRunner.ts](src/lib/server/jobs/chapterSummaryRunner.ts), launcher-gated per story) uses the same source selector and records its manifest as a `reviewed` revision of the same slot, inside its own transactions; it defers while the live worker is generating that slot, and the live worker defers to an open reviewed revision. The runner never writes backend jobs: its committed chapters are handed to the lifecycle owner, which enqueues only `rollup_arc`, `embed_memory_nodes`, and `sync_story_vault` for them. Incident-specific replacement limits live in recovery tooling ([summaryRecoveryIncidents.ts](src/lib/server/jobs/summaryRecoveryIncidents.ts), [chapterReplacementRecovery.ts](src/lib/server/jobs/chapterReplacementRecovery.ts)); retained manifests and receipts keep validating against them.

`jobs.rebuildSummaries` defaults to a dry run. Its `dryRun: false` mode queues [summaryRebuild.ts](src/lib/server/jobs/summaryRebuild.ts), which backs up primary-history sources and projections, stages generated chapters/arcs, revalidates the source snapshot and worker lease, and atomically replaces summary projections. It does not replay turns, world ticks, Director planning, thread reconciliation, or character updates; the rebuilt chapters are recorded as committed `historical` window revisions and open live revisions are invalidated, with no consumer jobs. Optional `resumeJobId` reuses validated drafts from a failed rebuild only when the story snapshot and historical generation policy match; changed source windows regenerate. Existing saved accounts also require the current source fingerprint; unchanged IDs alone cannot establish unchanged history. Alternate branches require a separate scoped rebuild. Progress and the backup path are saved in `backendJobs.metadata.summaryRebuild`.

[memoryCoverage.ts](src/lib/server/jobs/memoryCoverage.ts) reports extraction coverage against eligible source pairs, including missing, failed, outdated, waiting, and running work. The contiguous boundary stops at unresolved gaps. A later successful extraction does not repair an earlier source automatically.

Character continuity refresh runs in the chapter's `chapter_characters` job after every completed chapter, with the preceding chapter retained as a recovery window. The character-update service refines existing chapter proposals; automatic application checks the character version captured before refinement, leaving changed targets for review. Per-turn extraction still owns immediate state changes.

Use `jobs.status` and scoped `jobs.retry` through the engine gateway; failure classification lives in [failureClassification.ts](src/lib/server/jobs/failureClassification.ts). The retry policy in [outbox.ts](src/lib/server/jobs/outbox.ts) allows replay-safe types (including the deterministic `rollup_saga`), and also `summarize_chapter` and `rollup_arc` when their recorded failure is a missing model configuration (raised before any request or write); other failures of those types still need review. Wrapped database errors are recorded and classified by their server reason (for example a deadlock or timeout), without bound query parameters. Coverage, checkpoint/consolidation freshness, vault freshness, and vector-index freshness are different signals. Repeated retries do not fix provider-account or invalid-output causes.

[StoryMemoryPanel.svelte](src/lib/components/memory/StoryMemoryPanel.svelte) and [MemoryProcessingStatus.svelte](src/lib/components/story/MemoryProcessingStatus.svelte) expose processing and recall state. [mtheriosSummaryFormat.ts](src/lib/services/ai/context/mtheriosSummaryFormat.ts) removes audit/control noise while preserving the complete factual history. Prompt assembly prioritizes chapters not yet covered by an arc and bounded arc accounts, with explicit notices when history must be omitted.

When Actor Decisions selects a Jev model, [jev.ts](src/lib/server/turn/jev.ts) sends bounded choices and prioritized actor-scoped source IDs through the configured provider. The same typed decision path accepts the provider-specific Choice/Noul models in [decisionModels.ts](src/lib/contracts/decisionModels.ts), including hosted Kev 4B, Clef, Liquid D1, Perplexity Decider, Solar Decide, Mercury Decide, and NanoGPT's Decider variants. Questions in one Decisions request are treated as independent. Actor views come from bounded per-actor queries; being an event's target is not knowledge — only participation, witnessed/learned/shared links and belief evidence are. Changing embedding model or dimensions requires a separate Qdrant collection and a story-vault reindex before semantic wiki retrieval is fresh.
