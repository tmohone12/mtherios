# Phase 10 image infrastructure — 2026-09-23

Status: **partial implementation**, on the isolated MythEngine working copy. The image provider was not called with a paid credential during this run.

Migrations `0039_image_assets.sql` and `0040_image_job_identity.sql` add immutable asset records, project/game foreign keys, a unique origin-job receipt, and document cover identity with an independent cover revision. Project-only `generate_image` jobs are allowed without a dummy story. Before migration, the isolated PostgreSQL database was backed up to `data/phase10-assets-before.dump`; `pg_restore -l` verified the archive.

`imageAssets.ts` accepts only bounded PNG/JPEG/WebP signatures, writes opaque image keys under the server data root, records SHA-256 and scope, and validates bytes on read. `/api/assets/[assetId]` requires matching project/game scope and serves only public assets with private, no-store headers; GM-only assets remain available to server code but are not exposed by that route until an authenticated author read is designed. `content.cover.select` records a separate cover revision and document history; an old expected revision or a GM-only image for a public document is rejected.

New document creation calls `automaticCovers.ts` in the same transaction. It queues one stable job only when the project-wide switch is on and an enabled, supported image profile has a model and resolved key. It does not queue on copy, import, restore, or replacement. The switch is independent of GM and Assistant chat image switches. `imageJobs.ts` rechecks the relevant switch and document cover revision before provider spend, reuses an asset with the same origin job after a retry, and applies the asset only if the cover revision still matches. A stale result remains a stored, unapplied asset. Each job has one attempt to avoid an automatic second provider charge after an uncertain failure. Job metadata records the resulting asset URL and applied state; asset metadata retains reported usage. `imageProvider.ts` currently supports the configured OpenAI Images endpoint with bounded base64 response handling; it does not fetch provider-returned URLs. The request shape follows the [OpenAI Images API](https://developers.openai.com/api/reference/cli/resources/images/methods/generate).
