# Story-grounded character updates

Use this workflow when asked to expand or refresh an existing character's biography, appearance, or personality. Work within the named story; a character with the same name in another campaign is not the target.

1. **Resolve the target.** Read runtime status and the story list. Use the returned story ID verbatim: underscores in vault or index names do not replace hyphens in canonical IDs. Find the character through `characters` records and read its current revision, description, state, aliases, and source references.
2. **Gather both origins and current context.** Read the existing bio, early passages about upbringing, relevant chapters/arcs, and later developments. Search canonical names and former names separately when a combined display name misses results. Prefer original passages for decisive claims. Exclude noncanon/OOC transcript exchanges from narrative evidence; current author instructions are a separate input.
3. **Compose a coherent profile.** Preserve supported background and existing nuance. Include the user's explicit appearance and talent additions. Connect personality to established upbringing and demonstrated choices, including strengths, flaws, and tensions. Do not invent childhood events to explain a trait. Update superseded claims, such as an identity that was once unknown but is now revealed. Keep rumors, dreams, prophecy, uncertain parentage, NPC belief, and future plans distinct from established facts. A player profile describes tendencies without choosing the player's thoughts or actions.
4. **Prepare a narrow update.** Use `world.character.draftUpdate` / `mtherios_draft_character_update` for a reviewable application draft. It stays pending until the existing proposal review applies it. When the user directly authorizes a concrete edit through Codex, `world.record.patch` can apply the authored change with the freshly read `expectedVersion`. Send only changed fields. A draft proposes new facts as `state.developments`; approving it appends them and never rewrites the authored bio, personality, appearance or voice. To replace the bio itself, approve with a note beginning `retcon:` or edit it directly; for a directly revised bio, align `description` and `state.bio`. JSON state updates merge by default; do not send a sheet snapshot or use replacement mode. Preserve stats, capabilities, location, event memory, relationships, and unrelated metadata.
5. **Verify the result.** After applying, reread the canonical character and compare each changed field plus unrelated state. If another write changed the revision, reread and reconcile before retrying. Refresh the generated wiki through the existing sync path and verify the character page when archive output matters. A pending draft, saved record, fresh vault, fresh search index, rendered UI, and live GM request are separate evidence; report only what was checked.

The server implementation is [characterDrafts.ts](../src/lib/server/engine/characterDrafts.ts). Accepted draft updates flow through [canonRepair.ts](../src/lib/server/engine/canonRepair.ts). Manual edits use [worldRecords.ts](../src/lib/server/engine/worldRecords.ts). These shared paths serve UI and MCP; no separate character store is needed.
