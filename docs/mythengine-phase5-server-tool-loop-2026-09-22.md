# MythEngine Phase 5 server tool loop

Date: 2026-09-22. Phase 5's GM server path is implemented in the isolated MythEngine working copy on `codex/mythengine-overhaul`. The [overhaul plan](mythengine-overhaul-plan-2026-09-21.md) continues with Research in Phase 6, gameplay cards and dice in Phase 7, and the separate project Assistant in Phase 8.

## Delivered behavior

`agent.run.start/status/respond/cancel` use the existing engine gateway. A GM run is bound by the server to one project, game and `clientTurnId`. PostgreSQL migrations 0030–0032 store runs, normalized provider decisions, tool-call receipts, questions, provider usage and a cursor-ordered event log. `/api/engine/run-stream` replays persisted events after a sequence cursor. A run can pause without inserting a player/narrator entry or reserving a `syncOps` turn; another advancing turn in that game is rejected until the run completes, fails or is cancelled. Final narration goes through `processServerTurn` with the same `clientTurnId` and existing GM exploration callback, so its original idempotency and downstream work remain the turn owner.

The provider wrapper accepts complete native OpenAI-compatible or Anthropic tool calls. Providers rejecting native tools fall back to one strict JSON decision; partial stream fragments and prose are never interpreted as commands. Each normalized decision is persisted before dispatch, so an expired lease resumes the saved call rather than requesting a new choice from the provider. Each round permits one tool, with bounded context, response size, timeout and six-call ledger limit. The dispatcher derives GM authority from the run, checks current settings, and exposes bounded game reads/search/list, persisted `askUserQuestion`, and revision-checked `content.update` for unscoped game-owned documents. A mutation and its tool result/history attribution commit in one transaction. Canonical argument hashing survives JSONB key reordering; a call ID reused with different arguments is rejected.

Question responses use interaction revisions and stable option IDs. The same accepted answer replays safely; a different answer conflicts. Repeated model requests for the same answered choice complete from the existing answer instead of creating another card. Cancellation and expiry close pending interactions. Resume rebuilds canonical prompt context and keeps previously accepted observations; the context fingerprint excludes answer text so a changed fingerprint reflects prepared context or settings, not merely the response.
