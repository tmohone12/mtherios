# Chapter-only runner

This is a separate story-scoped workflow. The global job worker and wiki indexer can remain paused. It never claims `backend_jobs`, invokes the broad chapter processor, or generates arcs, plot state, character/campaign/faction updates, or old queued chapters.

## Activation

The launcher defaults to disabled. Deployment must apply `drizzle/0053_chapter_summary_runner.sql` and set `chapterRunnerEnabled: true` plus exactly one `chapterRunnerStoryId` (CLI equivalents: `--chapter-runner --chapter-runner-story <id>`). Keep `jobWorker: false` and `wikiAutoIndex: false`. These are deployment instructions, not authorization to modify a live launcher.

In that story's Chapters tab, inspect the boundary, next eligible range and limits. Choose a chapter count, cumulative USD ceiling, minimum interval and UTC expiry. The checkbox explicitly approves the displayed route and limits. Its defaults are proposals, not previously granted approval. Enable persists authorization; Pause stops new dispatches and publishing. A request already sent can finish and retain its draft. Refresh status shows the saved boundary, next range/due time, reservations and held receipt.

The daemon polls this one story every minute. It waits for the next 20 completed player/narration turns after the latest chapter's source boundary, then plans one exact source window. Existing chapters are reused. No old queue job is dispatched. The existing memory service configuration must already specify NanoGPT, its official API base URL and the exact model; reading it does not create or rewrite settings.

## Route and budget

Model: `xiaomi/mimo-v2.6-flash`. NanoGPT provider: `xiaomi`, quantization `fp8`. Requests pin `provider.only` and `provider.order`, disable fallbacks, require supported parameters and cap effective price at approximately $0.147/M input and $0.294/M output (caps round upward by $0.000000001/M to avoid floating-point metadata rejection). These prices already include the NanoGPT provider-selection markup. Reasoning is explicitly off. Transport retries are zero. Public endpoint metadata is checked before generation; a failed check sends no inference.

Each chapter reserves $0.033 before generation, at most three calls, 120,000 cumulative input tokens and 36,000 cumulative output tokens. Each call is capped at 50,000 conservative input tokens and 12,000 output tokens. Token cost ceiling is $0.028224000156; the conservative 1.134 allowance gives $0.032006017, rounded up to $0.033. The allowance is not an additional verified NanoGPT fee. A $0.31 cumulative approval therefore fits nine reservations ($0.297), with up to 27 calls, even when the count ceiling is ten chapters. Account credit and provider acceptance remain unknown until an authorized request. Provider price changes above the caps hold the attempt. Historical OpenRouter manifests remain readable and repeatable for already saved external drafts; they cannot dispatch new paid requests under the NanoGPT approval.

Approvals permit 1–100 chapters and at most $3.10, with a 1–10,080 minute interval and expiry within 90 days. Cumulative allocations and reservations survive pause, restart and changed approval limits; they never reset to create new budget. Choose explicit higher limits when exhausted. Calls can cost less than reservations; unused reservations are not silently reclaimed.

## Persistence and failure handling

The runner uses a persistent per-story activation/attempt ledger and advisory transaction locks. A ten-minute owner lease prevents simultaneous dispatch. Each provider stage reserves its request hash before sending. NanoGPT non-streaming requests explicitly ask for usage; the finalized payload is counted against the existing caps. The response-header `X-Request-ID` is stored as `billingRequestId`, separately from JSON/SSE `completionId`, and persisted before the response body is read. A header-persistence failure stops the attempt without retry. Missing billing IDs remain unknown; completion IDs are not substituted for a billing lookup.

A completed stage or retained draft can be reused after restart; a reserved, blocked or uncertain request cannot automatically replay. Credit/quota failures and held attempts expose actionable status with sanitized receipt identifiers. No credential-bearing error strings are returned. Historical receipts without these newer optional fields remain readable; adding fields does not authorize changing a held receipt or its budget.

An isolated operator may prepare a punctuation repair proposal with `proposeRecoveryEvidenceRepair`. It searches only the assigned evidence record for one unique literal span, allowing typographic apostrophe differences and a terminal period versus comma. It does not relax validation, accept paraphrases, or approve claims. `reviewRetainedRecoveryStage` requires an explicit semantic review bound to the full run, source, draft, raw-response and receipt hashes. It retains original text, usage, billing IDs and reservations and changes only the reviewed stage checkpoint. No public API exposes this action.

For a held split chapter with exactly one explicitly reviewed first-half attempt, `reviewRetainedRecoveryCompletion` can accept an explicitly reviewed full source-bound draft with the first ten accounts preserved exactly. Remaining accounts are externally authored; no unrequested provider stages are fabricated as completed. The import keeps the runner held, retains the entire attempt and budget, and blocks further provider generation. Publication remains a separate reviewed commit. Stale coverage, source changes, partial accounts, different first-half content, an enabled runner, or missing explicit review stop the operation.

Publishing validates exact source references/quotes, attribution and source order. This is automatic structural validation, not human semantic review or a guarantee against every summary error. The chapter, derived memory node, story sync version, recovery ledger and completed runner state commit atomically. Repeat commits do not increment the version or edit timestamps; failed commits roll back. Source/canonical changes hold a stale plan rather than widening the range.

The browser publication refresh imports only missing chapter IDs for the still-selected story. It does not replace canonical records, delete existing chapters, move the sync cursor, flush pending edits or overwrite local chapters. The ordinary existing full story projection remains a separate browser behavior.

## Validation and limits

New chapter-only runs use `server-evidence-references-v1`. The provider chooses one reference from each original record, in source order; it cannot submit free prose, quotations or character attribution. The server supplies exact bounded source excerpts and explicitly attributes them to the retained player/narration records. This produces condensed extractive memory rather than a newly paraphrased story. It prevents punctuation copying failures and semantic rewrites such as future orders becoming completed acts. Reference/account coverage, raw source substring validation and stale-source checks still apply. Unknown references, extra generated prose, missing records or malformed paid responses hold without replay. Split windows need two selector calls; the server combines the ordered accounts without a paid synthesis call. Legacy receipts/drafts keep their original protocol and identity.

`reconcileCommittedChapterRunner` is an explicit operator recovery action for a held activation whose external source-reviewed chapter and memory node have already committed. It checks exact runner/run/draft hashes and unchanged source/derived rows; keeps every allocation, reservation and uncertain prior request; records completion and an audit, clears only the resolved active manifest, and enables future chapters within the retained approval. A local reviewed save sends no inference and does not create another paid cadence interval: next due is no earlier than the latest retained paid stage's measured end plus the approved interval, or an existing later due time. Missing timing evidence holds. Ordinary future chapter publication still schedules the next chapter after the full approved interval. No public action bypasses uncertain responses.

Fixture tests cover gate/approval, 19-to-20 turn readiness, exact routing, transactional sync versions, idempotency, concurrency/restarts, uncertain responses, pause/resume with retained drafts, budgets/expiry/intervals and story-switch-safe client refresh. The isolated browser flow uses mocked inference and a disposable database. It does not validate real provider semantics, real account credit or the user's existing open browser.

Deployment and production activation require a specific spend approval. The global worker, indexer, arc runner and old queue remain untouched. Rollback pauses the new runner first and restores the accepted launcher/build; preserve generated chapters and ledger records rather than deleting them.
